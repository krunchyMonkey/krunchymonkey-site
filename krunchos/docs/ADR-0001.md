# ADR-0001 — Isolated KrunchOS frontend foundation

**Status:** Proposed for review. **Scope:** KMOS-001 through KMOS-004, GitHub issues #14–#17.

## Context

The published KrunchyMonkey site is a small no-build HTML/CSS GitHub Pages artifact. KrunchOS introduces multiple OS application views, a shared desktop/mobile launcher and nontrivial state. Directly rewriting the public root would prematurely replace the approved design baseline and could break existing legal/OAuth information URLs.

## Decision

Build KrunchOS as a self-contained React + strict TypeScript + Vite application under `krunchos/`. This is a **preview**, never included in the current public Pages allowlist. The standalone Vite build is runnable by cloning the repo and installing dependencies.

The layout is feature-first: `apps` owns typed application metadata; `shell/model` owns OS window state; each reusable component owns its directory, curated `index.ts` export and colocated tests; `features` owns project content; `styles` owns shared brand tokens. Desktop and mobile consume the same registry and feature components. No hidden framework, backend, or CMS is required.

The retro workstation visual design takes cues from owner-provided desktop/mobile concept references: beige panels, dark charcoal, amber accents, bitmap-inspired typography, pixel-ish buttons and simple window chrome. Reuse the **original monkey image** from the parent repository. Keep modern input ergonomics and accessibility.

## Alternatives considered

- Extend static HTML/CSS with more global DOM manipulation: minimizes dependencies, but complicates windows, routing, app composition and long-term testing.
- Replace the public root with a React SPA immediately: simpler repo structure, but risks a premature visual/deployment cutover and loss of public informational/privacy URLs.
- Adopt a UI framework/large desktop library: faster initial chrome, but more dependencies and less opportunity to demonstrate deliberate implementation of small components.

## Consequences

A separate app means temporary duplication of basic typography/tokens. The Vite dev server reads the approved logo from the parent repo using a relative import, so a clone of the full repository is necessary; it is packaged into the preview build by Vite.

The first slice supports local launcher/navigation and a single lightweight draggable window. Production routing, advanced window behavior, layout persistence, independently hosted demos and visual-parity acceptance remain later work.

## Release gate

Before shipping publicly: obtain owner-approved 1440px and 390px screenshots, merge the revised engineering charter, confirm CI, add production routing and preserved public pages, and explicitly authorize the production cutover. A draft PR or passing tests alone does not publish anything.
